# Experiment 010 — Qwen3-0.6B-Instruct Evaluation

**Date:** 2026-09-17  
**Phase:** Phase 2 — LLM research and selection  
**Status:** ⚠️ **DEFERRED — INVESTIGATION FLAGGED**  
Initial candidate evaluation completed, but the candidate is not currently considered deployable. Return to this experiment later if project time permits.

## Objective

Evaluate Qwen3-0.6B as a lightweight Apollo Lake candidate. The experiment tested basic English and Simplified Chinese generation, bidirectional translation, mixed English/Chinese interaction, a longer Chinese factual-summary workload, CPU inference, Vulkan/iGPU inference, and a small Vulkan `ngl` sweep.

The candidate was specifically investigated because Apollo Lake's goal is to find the smallest practical satisfactory model while maintaining useful conversational throughput on the Intel Celeron N3350 / Intel HD Graphics 500 system.

## Hardware / environment

- Lenovo IdeaPad 120S-11IAP
- Intel Celeron N3350 — 2 cores / 2 threads
- 4 GB installed RAM (~3.7 GiB visible to Linux)
- Intel HD Graphics 500 (APL 2)
- Alpine Linux 3.24.x, installed persistently to internal eMMC
- Kernel: 6.18.35-0-lts
- Model storage: `/opt/apollo-lake/models/qwen3-0.6b/`
- Inference runtime: llama.cpp 0.0.9564-r0
- Model: Qwen3-0.6B GGUF, Q4_K_M
- Model file size: 461.8 MiB
- CPU tests: 2 threads
- Swap: disabled for controlled inference measurements
- Controlled context size: 2048 tokens
- Reasoning: explicitly disabled with `--reasoning off`

## Model acquisition

The official Qwen3-0.6B GGUF repository did not contain the required Q4_K_M file at the tested URL. A Q4_K_M GGUF from `NANI-Nithin/Qwen3-0.6B-GGUF` was therefore used.

Downloaded file:

```text
Qwen3-0.6B-Q4_K_M.gguf
461.8M
```

The model loaded successfully with llama.cpp in a one-token load test.

## Memory / context investigation

The first normal conversation attempt used the model's default context configuration and failed during model loading:

```text
__vm_enough_memory: pid: 4592, comm: llama-cli, bytes: 4697624576 not enough memory for the allocation
llama-cli[4592]: segfault ... in libllama.so.0.0.9564
```

The requested allocation was approximately 4.38 GiB, exceeding the machine's approximately 3.7 GiB visible physical RAM.

A controlled context of **2048 tokens** was then used for subsequent inference. Normal short conversational tests loaded and ran successfully with this setting.

A separate Chinese long-form factual-summary test also produced a segmentation fault at one point. Repeating the same workload with `-c 2048` completed without a crash, although the generated factual content was poor. Therefore the exact cause of the first long-prompt crash was not treated as fully isolated from the context/memory configuration.

The kernel log also contained a separate `libvulkan_intel.so` segmentation fault during the broader Qwen3 testing session. The exact triggering invocation was not captured, so this is recorded as a stability observation rather than assigned a definitive cause.

## Controlled CPU configuration

Normal CPU tests used:

```sh
llama-cli \
  -m /opt/apollo-lake/models/qwen3-0.6b/Qwen3-0.6B-Q4_K_M.gguf \
  -t 2 \
  -c 2048 \
  -n 128 \
  -cnv \
  --reasoning off
```

This configuration was selected after the default context attempted an allocation larger than available physical RAM.

## CPU linguistic results

Observed:

Assessment: **pass**

### Simplified Chinese

### English → Chinese

### Chinese → English

Prompt:

> 请把下面这句话翻译成自然的英文：“我今天下午要去图书馆学习，因为明天有数学考试。”

Result:

The meaning was substantially understandable, but the tense was wrong (`I went` instead of an intended/future construction) and `today afternoon` was unnatural English.

Observed:

- Prompt: **10.4 t/s**
- Generation: **3.8 t/s**

Assessment: **partial pass**

### Mixed English/Chinese conversation

Prompt:

> 我今天在 UCL 上了一整天的 maths 课，现在感觉有点 tired。你觉得我今晚应该继续学习，还是早点休息？

Initial result: the model translated the mixed-language question into English rather than answering the underlying question.

After clarification:

> Oh, please answer 真正的问题

The model still repeated/rephrased the question rather than providing the requested advice.

Observed:

- Initial prompt: **11.4 t/s prompt, 3.6 t/s generation**
- Clarification: **10.7 t/s prompt, 3.6 t/s generation**

Assessment: **fail for the tested mixed-language conversational requirement**

## Additional Chinese factual-reliability test

Prompt requested a simple Chinese summary of *Romance of the Three Kingdoms* through Guan Yu's death.

The first attempt crashed with a segmentation fault. A repeat using the controlled 2048-token context completed, but the generated summary contained major factual and chronological errors, including incorrect descriptions of Guan Yu's relationships and historical sequence, and repeated the same year.

Observed generation on the successful controlled run: **3.7 t/s**.

Assessment: **fail for factual reliability on this tested historical-summary workload**

## CPU performance summary

Observed generation across the substantive CPU tests was:

- English: **3.8 t/s**
- Chinese: **3.8 t/s**
- English→Chinese: **4.0 t/s**
- Chinese→English: **3.8 t/s**
- Mixed conversation: **3.6 t/s**
- Controlled Chinese factual summary: **3.7 t/s**

Observed range: **3.6–4.0 t/s**.

This is above the project's **3.5 t/s generation target** in these individual runs. It does **not** yet establish the target as a sustained or statistically rigorous result.

Prompt-processing results were approximately **8.5–12.0 t/s** across the tested prompts, below the project's later **30 t/s prompt-processing target**. These prompt figures are secondary and should not be compared directly across different prompt lengths/content without a controlled prompt benchmark.

## Vulkan / iGPU setup

`llama-cli --list-devices` confirmed:

```text
Available devices:
  BLAS: OpenBLAS (0 MiB, 0 MiB free)
  Vulkan0: Intel(R) HD Graphics 500 (APL 2) (1875 MiB, 1688 MiB free)
```

Full offload was tested with:

```text
-ngl 100
```

For this model, values above the number of available model layers do not offload additional work; `100` therefore acts as an "up to all available layers" setting rather than literally meaning that more than all layers are moved.

## Vulkan `ngl` sweep

The same English conversational prompt was used for the sweep. Configuration remained controlled at 2 threads, 2048 context and reasoning off.

| Vulkan offload | Prompt | Generation |
|---:|---:|---:|
| `-ngl 0` (CPU) | **12.0 t/s** | **3.8 t/s** |
| `-ngl 1` | 4.4 t/s | 2.8 t/s |
| `-ngl 25` | 9.5 t/s | 3.6 t/s |
| `-ngl 50` | 12.0 t/s | 3.8 t/s |
| `-ngl 75` | 12.0 t/s | 3.8 t/s |
| `-ngl 100` | 12.0 t/s | **3.9 t/s** |

Interpretation:

- Very small partial offload was slower than CPU-only inference.
- Larger offload reached approximately CPU-level generation throughput.
- Full offload showed only a small observed advantage over CPU on the tested English prompt.
- No 10+ t/s generation result was observed.

These are individual measurements, not a statistically rigorous performance sweep.

## CPU vs Vulkan summary

Across the comparable English/Chinese workloads, CPU and full Vulkan generation were effectively tied at approximately **3.6–4.0 t/s** for Qwen3-0.6B.

Unlike Qwen2.5-1.5B, where Vulkan produced a substantial generation-speed improvement over CPU, Qwen3-0.6B is already small enough that the N3350 CPU is highly competitive with the HD 500 Vulkan path.

The result does not mean Vulkan is useless: full offload works successfully and may still matter for overall resource distribution or future models. It does mean that **no large generation-speed advantage was observed for this model**.

## ⚠️ Deferred investigation flag

**This experiment is deliberately paused and must not block the main Apollo Lake development path.** After a clean reboot, with swap disabled and the exact previously successful CPU command reproduced, Qwen3-0.6B again produced a segmentation fault. The same model also produced segmentation faults during the later Vulkan/iGPU attempts. The underlying cause has not been isolated.

The important control result is that this is **not evidence that llama.cpp, Alpine, or the Intel HD Graphics 500 Vulkan path is generally unusable**: Qwen2.5-1.5B subsequently ran stably on CPU and with Vulkan acceleration. The Qwen3 issue is therefore retained as an open engineering investigation rather than silently treated as resolved.

**Decision for the current project path:** defer Qwen3-0.6B investigation and proceed to the speech-system work. Revisit Experiment 010 if time permits.

## Post-experiment verification after reboot

A clean reboot was performed before the deferred investigation decision. Swap was then disabled again for controlled inference measurements.

The exact CPU command that had previously produced successful Qwen3 results was reproduced and again terminated with a **segmentation fault** during the conversational prompt.

For comparison, Qwen2.5-1.5B remained stable after reboot: **1.7 t/s CPU** and **2.5 t/s Vulkan/iGPU** on the same English prompt. Qwen2.5-0.5B was re-downloaded to persistent storage and ran on CPU at **2.2 t/s**, but its full Vulkan test also segfaulted.

These post-reboot results are verification observations rather than replacements for the original formal experiment measurements.

## Overall assessment

Qwen3-0.6B is currently promoted to the **provisional Apollo Lake leader** because it combines substantially higher observed generation throughput with a much smaller model footprint than the previously leading Qwen2.5-1.5B.

Key strengths:

- Very small Q4_K_M model footprint: **461.8 MiB**.
- Basic English generation passed.
- Basic Simplified Chinese generation passed.
- English→Chinese translation passed the tested task.
- Observed generation was consistently **3.6–4.0 t/s**, above the project's 3.5 t/s target in these individual runs.
- Full Vulkan offload works.
- CPU and Vulkan both achieve approximately the same generation range, giving flexibility in the eventual runtime configuration.
- 2048-token context permits normal short inference within the 4 GB system's memory envelope.

Important weaknesses / open issues:

- Chinese→English translation was only a partial pass because of tense and naturalness errors.
- Mixed English/Chinese conversational instruction following failed the tested requirement even after clarification.
- The tested Chinese historical-summary task produced major factual errors.
- Default model context caused an attempted ~4.38 GiB allocation and failure on the 4 GB machine.
- A separate Vulkan driver segmentation fault was recorded in the kernel log during the broader testing session; the exact triggering invocation was not captured.
- Prompt throughput is below the project's 30 t/s target in the observed interactive runs.
- Generation performance has not yet been tested for sustained 30-minute operation.
- More candidate models must be evaluated before final selection.

## Selection status

**Current provisional leader: Qwen3-0.6B Q4_K_M**

This is a provisional engineering decision and can be changed as soon as another candidate demonstrates a better combination of bilingual capability, instruction following, factual reliability, speed, stability and system-resource headroom.

Qwen2.5-1.5B remains an important comparison point because it demonstrated stronger tested mixed-language recovery and substantially benefited from Vulkan acceleration, despite its lower throughput.
